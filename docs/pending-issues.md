# 待處理問題清單

先前五個維度（狀態管理、遊戲邏輯、商城/購物車、效能渲染、代碼品質）交叉審查後，尚未處理的項目。已完成的優化不列在這份文件（詳見對話記錄）。依風險/影響程度排序，數字越小越優先，同一組件下的檔案結構如有異動請自行核對現況。

## P0 · 安全性與資料正確性

1. Blackjack、Baccarat 的洗牌種子仍由前端產生，沒有伺服器預先承諾種子，理論上可被竄改結果（Slots 之前已改成伺服器可驗證的種子式 RNG，這兩款遊戲還沒跟上）。
2. 錢包 hydrate 失敗時會把餘額顯示成 0，使用者可能誤以為錢真的不見了，應改成顯示錯誤狀態而非覆蓋成假資料。
3. 商品目錄 API 失敗時會靜默 fallback 成 mock 資料，使用者在瀏覽/加購階段完全不知道看到的是假資料，要到結帳才會報錯。

## P1 · 競態與健壯性

4. 免費領取/充值的冷卻與額度檢查仍有 TOCTOU 空窗（目前只有前端 pending 鎖防連點，沒有伺服器端原子保證）。
5. 結帳成功頁可能因瀏覽器 bfcache「返回」恢復到舊的送出狀態，目前的送出鎖只存在元件實例記憶體中，沒有頁面層防護。
6. 結帳表單沒有 schema 驗證，只在送出時做簡單字串檢查，沒有逐欄位即時反饋。
7. 錢包相關 Header/摘要元件目前是訂閱整包 balances 物件，任一幣別變動都會觸發不必要的重渲染。

## P2 · 遊戲邏輯一致性

8. Blackjack 狀態機定義了 dealing、dealer_turn 等狀態，但實際流程沒有真正使用，型別與行為不一致。
9. 下注相關常數（最低/最高下注、可選籌碼等）在 Blackjack 與 Baccarat 各自維護一份，容易改一邊漏改另一邊。
10. Slots 的開獎機率邏輯還沒有針對機率分佈本身的統計測試（目前的測試只驗證「同種子同結果」的決定性，沒有驗證賠付分佈是否符合設計）。

## P3 · 效能

11. 全站沒有使用 React.memo，商品/遊戲卡片列表在篩選時容易整批重渲染。
12. `next.config` 沒有設定 `experimental.optimizePackageImports`。
13. Header Logo 常駐使用 drop-shadow 濾鏡疊加動畫（非 GPU 合成屬性），且設了 image priority，可能跟真正的首屏大圖搶頻寬。
14. 購物流程沒有全域 Toast，加入購物車只有面板內一行文字提示，容易被忽略。
15. 運費、購買上限、可選數量等常數散落在多個檔案，數值彼此不一致（例如加購面板限制與購物車實際可修改上限不同）。

## P4 · 代碼品質與維護性

16. Supabase client 沒有綁定 generated types，多處用 `as unknown as` 之類的斷言繞過型別檢查。
17. 沒有 i18n 基礎設施，介面中英文字串混用（例如某些狀態標籤是英文，說明文字卻是中文）。
18. 交易類型顯示標籤等小工具，仍有分散在不同元件各自實作一份的情況。
